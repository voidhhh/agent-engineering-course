# 第 1 讲：Agent 系统全景

## 学习目标

能够区分 Model、Tool、Agent、Workflow、MCP、Skill、Framework 与 Harness，并为一个真实请求标注控制权和状态归属。

## 1. 为什么要分层

“Agent 能完成任务”并不能说明能力来自哪里。同一个模型接入不同工具、上下文和循环后结果可能明显不同；同一个 Harness 更换模型也会改变决策质量。如果不先拆层，模型改进、工具改进和运行时改进会被混在一起，评测失去解释力。

最小系统包含四类实体：用户提出目标；模型生成文本或结构化动作；宿主程序验证并执行动作；外部系统保存事实或产生副作用。Agent 是这四者围绕任务形成的闭环，而不是模型本身。

## 2. 八层心智模型

1. **Model**：根据当前上下文预测下一步输出。它不直接访问数据库或操作系统。
2. **Tool**：确定性能力接口，定义名称、描述、参数、返回值和风险。
3. **Agent Loop**：把模型输出解释为工具调用，把结果送回模型，直到终止。
4. **MCP**：让工具、资源和提示模板通过标准协议被发现和调用。
5. **Skill**：可按需加载的过程知识，说明一类任务应该怎样完成。
6. **Framework**：提供 Agent、Runner、路由、会话等开发抽象。
7. **Harness**：负责长期运行所需的上下文、状态、工具、沙箱、审批、恢复和 Trace。
8. **Product/Gateway**：提供用户界面、渠道、账号、设备和业务工作流。

## 3. 控制权分配

模型适合做语义理解、方案选择和不确定性判断。宿主必须掌握参数验证、权限判定、事务提交、状态持久化、预算和终止。不能因为模型“承诺不会执行危险命令”，就取消宿主策略；自然语言承诺不是安全边界。

一次典型请求的数据流是：宿主组装上下文和工具 schema；模型返回 tool call；宿主校验 schema、策略和审批；工具执行；结果写入会话与 Trace；模型基于观察继续或给出答案。

## 4. 易混淆边界

- Workflow 预先规定路径，Agent 在运行时选择路径；二者可以组合。
- MCP 只规定连接和消息语义，不替宿主做业务授权。
- Skill 是“如何做”的过程资产，Tool 是“可以做什么”的执行能力。
- Memory 是可持久化信息，Context 是当前这一次模型调用真正看到的 Token。
- 多 Agent 不是更高级的默认形态，而是任务隔离、并行或权限分工的一种选择。

## 5. 失效模式

最常见的架构错误包括：把所有聊天记录当作上下文；把 MCP Server 当作可信安全域；让模型自己决定是否越权；没有全局步数预算；工具返回整份大文档；多个并发 Run 同时写同一 Session；用最终答案评分却不检查副作用。

## 实验

选择“创建任务并返回编号”这一请求，画出用户、Host、Model、Agent Loop、Tool Registry、Task Store、Approval Policy 和 Trace Store。为每条箭头标注数据结构，为每个组件标注“概率性/确定性”和“是否持久化”。

## 验收问题

1. 模型为什么不能直接拥有数据库凭据？
2. MCP Server 暴露了工具后，谁决定用户能否调用？
3. Skill 与系统提示的主要差异是什么？
4. 更换 Harness 时，哪些变量必须保持一致才能比较？
