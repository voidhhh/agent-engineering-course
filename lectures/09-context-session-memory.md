# 第 9 讲：Context、Session 与 Memory

## 学习目标

区分模型当下可见的 Context、一次对话的 Session、可跨会话使用的 Memory，以及用于恢复执行的 Checkpoint。

## 1. 四种状态不是同一个东西

| 概念 | 回答的问题 | 典型载体 | 主要风险 |
|---|---|---|---|
| Context | 本次模型调用看见什么？ | messages、工具定义、检索片段 | 超窗、提示注入、重复 |
| Session | 这段交互属于谁、进行到哪？ | 数据库行、会话 ID | 串话、竞态、过期 |
| Memory | 哪些信息值得以后召回？ | 事实、偏好、摘要、索引 | 错误固化、污染、隐私 |
| Checkpoint | 中断后如何继续同一次运行？ | 状态机快照、待审批调用 | 重复副作用、版本不兼容 |

把所有历史直接塞回提示词，只是在重放消息，并没有解决状态建模问题。

## 2. Context 是编译产物

可把上下文构建理解为一次编译：从系统规则、当前输入、会话历史、检索结果、Skill 内容和工具模式生成受预算约束的模型输入。构建器应明确优先级、来源、长度、信任级别和去重规则。压缩不是简单截断；摘要必须保留未完成承诺、关键工具结果和审批状态。

## 3. Memory 是写入策略与召回策略

Memory 至少包含 `candidate → validate → store → retrieve → use → expire` 六个阶段。写入前要判断事实来源、稳定性、敏感性和有效期；召回时要记录为何命中；使用时仍需允许当前证据覆盖旧记忆。模型说“记住了”不等于存储已提交。

## 4. 一致性与隔离

Session 更新需要乐观锁或事务版本。并发运行若共享一份消息列表，会产生顺序不确定和重复工具结果。审批暂停时，应持久化原调用 ID、参数摘要、策略版本和恢复令牌；恢复不是创建一条新用户消息。

## 5. 实验

为连续实验实现 SQLite Session Store，加入 `revision` 字段和条件更新；设计三种上下文策略：全量、滑动窗口、摘要加最近消息。使用相同的 12 轮任务比较 Token 预算、答案一致性和未完成事项保留率。

### 验收标准

- 两个会话不会互相读取消息；
- 并发更新冲突可检测，不静默覆盖；
- 摘要后仍保留待执行工具调用和约束；
- Memory 条目包含来源、时间和可删除标识。
