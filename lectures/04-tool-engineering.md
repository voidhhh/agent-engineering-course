# 第 4 讲：Agent 工具工程

## 学习目标

把传统 API 重新设计成适合非确定性调用者使用的工具契约，并覆盖安全、成本和恢复问题。

## 1. Agent 工具与普通函数的差异

普通函数通常由知道接口的程序员调用；Agent 工具由模型根据自然语言描述选择。接口文档会直接影响行为，因此描述、名称、返回值和错误信息都是运行时设计的一部分。

工具应对应可理解的任务动作。太细会迫使模型拼装大量步骤，太粗会隐藏不可审计的副作用。理想粒度能让一次调用产生清晰、可验证的业务结果。

## 2. 输入设计

输入应使用明确枚举、单位、格式和默认值。避免同时接受多种同义字段。对文件路径、URL、SQL、命令和资源标识符实施宿主验证；JSON Schema 只解决结构合法性，不解决路径穿越、注入和权限。

## 3. 输出设计

模型需要有助于下一步决策的信息，而不是底层系统全部返回。输出包含稳定字段、结果摘要、可恢复错误和必要的资源标识。大结果应返回句柄、分页信息或聚合结果，避免把日志和二进制内容塞入上下文。

## 4. 副作用与幂等

写操作必须有清晰风险等级、预览和审批机制。调用编号或业务幂等键用于防止网络重试、会话恢复或模型重复请求造成二次提交。幂等缓存必须考虑作用域，不能让不同用户共享同一敏感结果。

## 5. 错误分类

错误至少分为：参数不可恢复、权限拒绝、需要用户输入、临时依赖失败、超时和内部缺陷。把所有异常变成“tool failed”会导致模型盲目重试。返回给模型的信息应足够制定下一步，同时隐藏堆栈、密钥和内部拓扑。

## 6. 工具 Eval

不仅测 handler，还要测模型能否选对工具、参数是否正确、输出是否帮助完成任务、错误后是否采用正确恢复策略。工具名称或描述的修改也可能造成回归，应进入 Eval。

## 实验

为 `add_task` 添加风险标记和审批；为重复 call id 添加缓存；构造同名工具、模糊描述、超大结果和临时异常，对比模型或 ScriptedModel 的轨迹。
